# Walls And Table Tests
M05 · Stage 4 · Schema · Lesson 2 · about 6 min · 23 Oct 2026

**Video slot:** provider `rosequest` · id `TO CONFIRM` · type `v` · key `M05-L2`

**You can:** You can name the eight walls and describe the table tests that must pass before the Schema gate.

Theo's cousin works at a grooming salon. One morning, the booking app the salon used showed her another salon's client list, names and phone numbers included. It was fixed within a day, but the trust was gone. When Theo started helping to plan Trimtable, he wanted to be sure it could never do that. At first he wrote, the data is private, in his notes. Then he realised that sentence proved nothing. What he needed was a test for each table that could actually fail, run from outside, with a date beside the result.

In the factory, a wall is a rule that keeps two parties' data apart. The simplest picture has three walls. Owner from owner keeps one reseller's businesses away from another reseller's. Business from business keeps one salon's records away from the next salon's. Customer from customer keeps one customer's details private inside a single business. The third wall always sits inside the second, never instead of it: check the business first, then the customer. Trimtable has no reseller above it, so the first wall has nobody on the other side yet.

The full set has eight walls, numbered W1-W8, and most codes on the idea card point to one. W1 is the brand wall, between businesses. W2 is the member wall, between customers. W3 is the layer-above wall, for parties sitting above a business. W4 is the staff wall, for roles, guests and view-as access. W5 is the membership wall, about who can join and belong, and whose name is shown. W6 is the public wall, for strangers who are signed out. W7 is the data-out wall, for data leaving the app. W8 is the sensitivity hold, for health or children's data.

Stage 4 ends with table tests, section 4.4 of the document. The test depends on the kind of table. Application tables hold a business's own records, like bookings. Each one gets a brand-wall read: sign in as tenant A and try to read tenant B's rows. Tenant A must see none. User tables hold one person's own things. Each one gets a user-wall read: one user must not see another user's rows. Control tables hold the app's own settings, and each gets an anonymous read, sent signed out, which has to return 401.

401 is a status code, a number a web server sends back with every answer. 401 means the request was refused because nobody is signed in. For a control table, that is exactly the answer you want a stranger to get. If the anonymous read returns 200 instead, which means success, and hands back rows, the table is open to the whole internet. That is a stop. The fix comes before anything else, and then the test is run again until it returns 401. A pass is only a pass when the stranger gets nothing.

Some tables are shared on purpose. Imagine one dog's record that two breeders both hold a claim on, with each allowed to see different fields. A field is one column in one row. A shared row carries no tenant id, so a normal row-level test looks for a tenant tag, finds none, and reports all clear, while the wrong fields leak. That is why the rule says a row-level test passes while leaking. On a shared table the leak test must be field-level: check that each claim sees only the fields it is allowed to see.

A test without a result is just a hope. So the stage is finished only when every Launch table and every Base table has at least one test with a dated result. Launch tables are the ones the first version uses. Base tables are the ones that come with the base the app started from. The tests are run from outside, as a real visitor would, not by asking the builder whether it worked. A sentence in the notes, such as the data is private, never counts. Only a test that could fail, and did not, counts.

Then comes the Schema gate. It sits between Stage 4 and Stage 5 and asks: tables probed, names re-read? Like the Base gate, it is automatic. When every Stage 4 checklist line is done, and no section of the document still says pending, the engine moves the app on without anyone clicking yes. That only works because the tests are plain. A probe returned 401 or it did not. A name matches the spec or it does not. Next comes Stage 5, where test businesses and test people are set up. First, the recap.

## Recap
- Eight Walls W1-W8 Keep Parties Apart
- Brand-Wall, User-Wall And Anonymous 401 Table Tests
- Shared Tables Need Field-Level Tests, Then Auto Schema Gate
- **Why It Matters:** A Test That Can Fail Is The Only Proof

## Quiz
1. Which wall keeps one business's data away from another business?
   - A) W1 Brand Wall
   - B) W6 Public Wall
   - C) W7 Data-Out Wall
   - D) W8 Sensitivity Hold
   - Answer: A. W1, the brand wall, sits between businesses.
2. What should an anonymous read of a control table return?
   - A) 200 with rows
   - B) A list of tenants
   - C) 401
   - D) The sales page
   - Answer: C. 401 means the signed-out request was refused, which is the pass.
3. Why is a row-level test not enough on a shared table?
   - A) Shared tables have no rows
   - B) It is too slow
   - C) Shared tables are always public
   - D) A shared row has no tenant id, so the test can pass while fields leak
   - Answer: D. On a shared table the leak test must be field-level, because a row-level test passes while leaking.
4. Who moves the app through the Schema gate?
   - A) A person always clicks yes
   - B) The engine, automatically, when every line is done
   - C) The customer
   - D) The reseller club
   - Answer: B. Schema is an auto gate: tables probed and names re-read, then the engine moves the app on.
