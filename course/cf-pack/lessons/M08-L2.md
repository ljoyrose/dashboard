# The Launch Walk And Boosts
M08 · Stage 7 · Launch · Lesson 2 · about 6 min · 23 Oct 2026

**Video slot:** provider `rosequest` · id `TO CONFIRM` · type `v` · key `M08-L2`

**You can:** You can name the checks that come before the Launch gate and explain why the weekly boost is still only proposed.

Maya is twelve. She tried the new Stayproof site on her laptop, signing up as a brand-new kennel worker, and everything worked. She was ready to say it could launch. Then she tried again on her phone. The sign-up email arrived, she tapped the link, and the page that opened had forgotten who she was. On the laptop, she had opened the email link in the same browser. On the phone, it opened somewhere new. Launch tests have to walk the whole journey, as a brand-new person, on desktop and on phone.

Before launch, the leak check runs one last time, and it is strict. Every table is tested, with negative cases, using two accounts. Not only the tables a screen happens to use, but every one, including old and forgotten ones. A negative case, as you know, checks that something forbidden really fails. The result sets the app's leak status: Ln for tested with no leak, or Ly for a leak found. An app showing Ly does not launch. In the factory's gate set, Leak is a check inside the Launch gate, not a separate gate.

Next comes the launch walk. Before the gate, a brand-new account for each brand walks the whole journey on the live site, on desktop and on phone, including email links opened on the phone. The journey map is the list of every step a person takes, from the first page to the app's core action, and it includes steps the factory does not build itself, like the sign-up email. Maya's phone problem is exactly what this walk is there to catch. An onboarding walk for each type of user follows the same idea.

Then comes the user-switch test, a standard check on every app. In one browser, sign in as user A and set a display name. Sign out. Sign in as user B. User B must see none of user A's name, footer text or settings. This catches a sneaky kind of leak, where the browser remembers something from the last person. On a shared family computer, or a laptop on a kennel's front desk, that really matters. It sounds simple, and it is, but real apps have failed this test more than once.

Money is tested for real. Checkout is tested on the live link with a 100 percent off test code: buy, sign in, and get access. Checkout never works in preview, so it has to be the live link. A real payment and a refund are also run from start to finish. Around this sit other duties due before launch: legal and consent pages live, with the marketing box left unticked, a security review before publishing, and proof that a user can delete their account and export their data, and that both actually work.

The support route is tested too, so a real person with a problem can actually reach help. Then comes the Launch gate, from 7 to 8. Its question is: open it to real users? The factory owner always decides this one. There is no auto-pass here. The engine describes it as Leak, Launch and Live in one move: the leak check passed, the launch walk done, and the first real user proved from start to finish. After a yes, the app leaves the build board and appears only in Operate.

What about growing the app after launch? The factory's template has a weekly boost line: a weekly proposal of ways to help the app get found, using parts from the Boost shelf, such as public pages, reviews, search visibility and funnels. But be clear about its status. The weekly boost is marked PROPOSED. It sits in the template as an idea that has not been ruled on, so this course teaches it as a proposal, not as a rule. In the factory, a proposal counts for nothing until the live system actually does it.

So before an app opens to real users, it passes a leak test on every table with two accounts, a launch walk on desktop and phone, a user-switch test, a live checkout test, legal and consent checks and a tested support route. Then the factory owner says yes at the Launch gate. Scheduled jobs switch on: the leak probe, the backup and the credit watch. Maya's phone found a real gap, and now the walk finds that kind of gap every time. Next module: how a live app is watched every single day.

## Recap
- Leak Test Every Table With Two Accounts
- Walk The Journey New, On Desktop And Phone
- The Owner Always Decides The Launch Gate (7-8)
- **Why It Matters:** Real Users Deserve An App Proved On Every Path

## Quiz
1. Why does the launch walk include a phone?
   - A) Phones are faster to test on
   - B) The sales page is only shown on phones
   - C) Phones never need a sign-in
   - D) Email links opened on a phone can break a journey that works on desktop
   - Answer: D. The walk covers desktop and phone, including email links opened on the phone, because journeys can break between devices.
2. What does the user-switch test check?
   - A) That two users can share one account
   - B) That user B sees none of user A's name or settings in the same browser
   - C) That users can switch brands freely
   - D) That the owner can sign in as anyone
   - Answer: B. Signing in as A, then out, then in as B in one browser shows whether anything of A's is left behind.
3. Why is checkout tested on the live link?
   - A) Checkout never works in preview
   - B) The live link is free to use
   - C) Preview has no buttons
   - D) The test code only works on phones
   - Answer: A. Checkout does not work in preview, so the 100 percent off test code is used on the live link.
4. What is the status of the weekly boost?
   - A) A gate the owner must pass
   - B) A rule that runs every day
   - C) Proposed, not yet a rule
   - D) Retired and no longer used
   - Answer: C. The weekly boost line is marked PROPOSED, so it is taught as an idea, not a rule.
