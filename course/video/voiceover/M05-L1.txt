How The System Makes The Tables
(Read at about 130 words a minute. UK English.)

Nia keeps the spreadsheet for her family's walking group, so when she heard Stage 4 was about tables, she thought it would be easy. She planned to add columns as she went, and rename them whenever better names came to mind. Then she learned two facts about the build platform. Renaming a table or column destroys every row in it, and still reports success. And changing who can read a table after it is made costs a paid building turn. So she changed her approach. Plan every table first, set it right at birth, and write down why it exists.

Stage 4 is called Schema. A schema is the plan of the tables that hold the data: which tables exist, which columns each one has, and who may read or write them. A column is one field in a table, like a dog's name or a booking date. Stage 4 sits in the Rig room, together with Stage 5, and it is free. Nothing here is built by the paid builder. The tables are built by hand, then proved by reading them back, which is called a re-read. Free work now saves paid work later.

Where does the list of tables come from? Not from guessing. The kits chosen earlier each bring their own tables. K00, the floor, brings seven: tenants, tenant users, roles, permissions, consents, usage channels and events. K02, booking, adds bookings, availability slots and resources. The codes on the idea card then shape the columns. If TEN (0-6) is 2 or more, several businesses share the app, so every table holding a business's data needs a tenant id column, which says which business owns each row. A tenant is one business using the app.

Before anything is created, the tables and columns are written out as a spec, short for specification, saved as a CSV file. A CSV is a plain file of rows and columns that any program can open. The spec is never left as loose prose, because nobody can test a paragraph. Every name is checked against the naming standard, so one idea always has one name. Then the tables are built by hand, for free, and each one is read back to prove it exists exactly as written. A copied base is also swept for ghost columns, ones it inherited but does not use.

Every table has an access mode, a setting that says who may read and write its rows. Here are some examples. Public means anyone can read, even when signed out. User scoped means each row belongs to the signed-in person who made it. Anonymous writable means a stranger can add rows without signing in. A role gate limits a table to people with a given role, such as staff. The access mode is set when the table is created, which is free. Changing it afterwards is a billed builder turn. So the mode is decided on paper first.

Deciding a mode is not the same as having it. So each table gets an anonymous probe. A probe is a test request, and anonymous means it is sent with nobody signed in, the way a stranger on the internet would arrive. If a table is meant to be private and the probe gets rows back, something is wrong, and it is fixed before going further. The codes set what is allowed. Litterline has POST (0-2) at 0, so no table should take writes from a stranger. VIEW (0-2) at 1 means only link-holders may read anything signed out.

The last piece is the table register, section 4.0 of the app's document. Every table gets one row in it, with the reason the table exists, its role gate and who may write to it. This sounds like paperwork, but it prevents a costly mistake. A table is never removed just because no code seems to read it. Removing a table needs a person's dated ruling. Without a register, a table that looks unused might hold the one record a business needs on inspection day, and deleting it would be very hard to undo.

One rule from the duties file is worth learning by heart. Never rename a table or column. A rename destroys every row and still returns a success message, so nobody notices until the data is gone. If a name must change, the safe way is to add the new column, copy the data across, which is called migrating, and leave the old one unread. Plan, spec, build by hand, set the mode, probe, record. That is how Stage 4 makes its tables. Now a short recap before we meet the walls.
