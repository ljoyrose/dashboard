## M05-L1 · How The System Makes The Tables
**Outcome:** You can explain how codes and kits decide the tables, and how each table is built, set and recorded.  
**Length:** 773 words · about 5.9 min · Today

**Opener (Epiphany Bridge (light)):** Backstory: Nia keeps a spreadsheet for her family's walking group and thought tables would be easy. · Desire: She planned to add and rename columns as she went. · Wall: On the build platform a rename destroys every row, and changing who can read a table later costs a paid turn. · Epiphany: Plan every table first, set it right when it is created, and write down why it exists.

| # | On Screen | Narration |
|---|---|---|
| 1 | Nia Thought Tables Were Easy | Nia keeps the spreadsheet for her family's walking group, so when she heard Stage 4 was about tables, she thought it would be easy. She planned to add columns as she went, and rename them whenever better names came to mind. Then she learned two facts about the build platform. Renaming a table or column destroys every row in it, and still reports success. And changing who can read a table after it is made costs a paid building turn. So she changed her approach. Plan every table first, set it right at birth, and write down why it exists. |
| 2 | A Schema Is The Plan Of Tables | Stage 4 is called Schema. A schema is the plan of the tables that hold the data: which tables exist, which columns each one has, and who may read or write them. A column is one field in a table, like a dog's name or a booking date. Stage 4 sits in the Rig room, together with Stage 5, and it is free. Nothing here is built by the paid builder. The tables are built by hand, then proved by reading them back, which is called a re-read. Free work now saves paid work later. |
| 3 | Codes And Kits Decide The Tables | Where does the list of tables come from? Not from guessing. The kits chosen earlier each bring their own tables. K00, the floor, brings seven: tenants, tenant users, roles, permissions, consents, usage channels and events. K02, booking, adds bookings, availability slots and resources. The codes on the idea card then shape the columns. If TEN (0-6) is 2 or more, several businesses share the app, so every table holding a business's data needs a tenant id column, which says which business owns each row. A tenant is one business using the app. |
| 4 | A Spec First, Then Built By Hand | Before anything is created, the tables and columns are written out as a spec, short for specification, saved as a CSV file. A CSV is a plain file of rows and columns that any program can open. The spec is never left as loose prose, because nobody can test a paragraph. Every name is checked against the naming standard, so one idea always has one name. Then the tables are built by hand, for free, and each one is read back to prove it exists exactly as written. A copied base is also swept for ghost columns, ones it inherited but does not use. |
| 5 | Access Modes Say Who Can Read | Every table has an access mode, a setting that says who may read and write its rows. Here are some examples. Public means anyone can read, even when signed out. User scoped means each row belongs to the signed-in person who made it. Anonymous writable means a stranger can add rows without signing in. A role gate limits a table to people with a given role, such as staff. The access mode is set when the table is created, which is free. Changing it afterwards is a billed builder turn. So the mode is decided on paper first. |
| 6 | Probe Every Table While Signed Out | Deciding a mode is not the same as having it. So each table gets an anonymous probe. A probe is a test request, and anonymous means it is sent with nobody signed in, the way a stranger on the internet would arrive. If a table is meant to be private and the probe gets rows back, something is wrong, and it is fixed before going further. The codes set what is allowed. Litterline has POST (0-2) at 0, so no table should take writes from a stranger. VIEW (0-2) at 1 means only link-holders may read anything signed out. |
| 7 | Every Table Gets A Register Row | The last piece is the table register, section 4.0 of the app's document. Every table gets one row in it, with the reason the table exists, its role gate and who may write to it. This sounds like paperwork, but it prevents a costly mistake. A table is never removed just because no code seems to read it. Removing a table needs a person's dated ruling. Without a register, a table that looks unused might hold the one record a business needs on inspection day, and deleting it would be very hard to undo. |
| 8 | Never Rename, Add And Migrate Instead | One rule from the duties file is worth learning by heart. Never rename a table or column. A rename destroys every row and still returns a success message, so nobody notices until the data is gone. If a name must change, the safe way is to add the new column, copy the data across, which is called migrating, and leave the old one unread. Plan, spec, build by hand, set the mode, probe, record. That is how Stage 4 makes its tables. Now a short recap before we meet the walls. |

**Recap**
- Kits Bring The Tables, Codes Shape The Columns
- Set Access Mode At Creation, Then Probe Signed Out
- Every Table Gets A 4.0 Register Row And Reason
- Why it matters: Tables Planned Once Are Cheap, Fixed Later Are Not

**Quiz**
1. What is a schema? A) The sales plan · B) The plan of the tables that hold the data · C) A type of brick · D) The launch checklist · **Answer B**: A schema is the plan of the tables, their columns and who may read or write them.
2. Why is the access mode set when a table is created? A) Because it looks tidier · B) Because the customer asks for it · C) Because only resellers can change it · D) Because setting it then is free and changing it later is a billed turn · **Answer D**: Setting the mode at creation is free; changing it afterwards costs a builder turn.
3. What does an anonymous probe do? A) Sends a test request with nobody signed in · B) Deletes old tables · C) Renames columns · D) Sends emails to customers · **Answer A**: It checks a table the way a signed-out stranger would reach it.
4. What is the safe way to change a column name? A) Rename it directly · B) Delete the table · C) Add a new column, migrate the data, leave the old one unread · D) Ask customers to type the data again · **Answer C**: A rename destroys every row, so the factory adds, migrates and leaves the old column unread.

## M05-L2 · Walls And Table Tests
**Outcome:** You can name the eight walls and describe the table tests that must pass before the Schema gate.  
**Length:** 761 words · about 5.9 min · Today

**Opener (Epiphany Bridge (light)):** Backstory: Theo's cousin once saw another salon's client list inside the booking app her salon used. · Desire: Theo wanted to be sure Trimtable could never do that. · Wall: Writing that the data is private proved nothing. · Epiphany: Each table needs a test aimed at its wall, run from outside, that could fail, with a dated result.

| # | On Screen | Narration |
|---|---|---|
| 1 | Seeing Someone Else's Clients | Theo's cousin works at a grooming salon. One morning, the booking app the salon used showed her another salon's client list, names and phone numbers included. It was fixed within a day, but the trust was gone. When Theo started helping to plan Trimtable, he wanted to be sure it could never do that. At first he wrote, the data is private, in his notes. Then he realised that sentence proved nothing. What he needed was a test for each table that could actually fail, run from outside, with a date beside the result. |
| 2 | A Wall Keeps Two Parties Apart | In the factory, a wall is a rule that keeps two parties' data apart. The simplest picture has three walls. Owner from owner keeps one reseller's businesses away from another reseller's. Business from business keeps one salon's records away from the next salon's. Customer from customer keeps one customer's details private inside a single business. The third wall always sits inside the second, never instead of it: check the business first, then the customer. Trimtable has no reseller above it, so the first wall has nobody on the other side yet. |
| 3 | The Eight Walls W1-W8 | The full set has eight walls, numbered W1-W8, and most codes on the idea card point to one. W1 is the brand wall, between businesses. W2 is the member wall, between customers. W3 is the layer-above wall, for parties sitting above a business. W4 is the staff wall, for roles, guests and view-as access. W5 is the membership wall, about who can join and belong, and whose name is shown. W6 is the public wall, for strangers who are signed out. W7 is the data-out wall, for data leaving the app. W8 is the sensitivity hold, for health or children's data. |
| 4 | Each Table Gets The Right Test | Stage 4 ends with table tests, section 4.4 of the document. The test depends on the kind of table. Application tables hold a business's own records, like bookings. Each one gets a brand-wall read: sign in as tenant A and try to read tenant B's rows. Tenant A must see none. User tables hold one person's own things. Each one gets a user-wall read: one user must not see another user's rows. Control tables hold the app's own settings, and each gets an anonymous read, sent signed out, which has to return 401. |
| 5 | A 401 Means Not Allowed In | 401 is a status code, a number a web server sends back with every answer. 401 means the request was refused because nobody is signed in. For a control table, that is exactly the answer you want a stranger to get. If the anonymous read returns 200 instead, which means success, and hands back rows, the table is open to the whole internet. That is a stop. The fix comes before anything else, and then the test is run again until it returns 401. A pass is only a pass when the stranger gets nothing. |
| 6 | Shared Tables Need Field-Level Tests | Some tables are shared on purpose. Imagine one dog's record that two breeders both hold a claim on, with each allowed to see different fields. A field is one column in one row. A shared row carries no tenant id, so a normal row-level test looks for a tenant tag, finds none, and reports all clear, while the wrong fields leak. That is why the rule says a row-level test passes while leaking. On a shared table the leak test must be field-level: check that each claim sees only the fields it is allowed to see. |
| 7 | Every Test Has A Dated Result | A test without a result is just a hope. So the stage is finished only when every Launch table and every Base table has at least one test with a dated result. Launch tables are the ones the first version uses. Base tables are the ones that come with the base the app started from. The tests are run from outside, as a real visitor would, not by asking the builder whether it worked. A sentence in the notes, such as the data is private, never counts. Only a test that could fail, and did not, counts. |
| 8 | The Schema Gate Passes By Itself | Then comes the Schema gate. It sits between Stage 4 and Stage 5 and asks: tables probed, names re-read? Like the Base gate, it is automatic. When every Stage 4 checklist line is done, and no section of the document still says pending, the engine moves the app on without anyone clicking yes. That only works because the tests are plain. A probe returned 401 or it did not. A name matches the spec or it does not. Next comes Stage 5, where test businesses and test people are set up. First, the recap. |

**Recap**
- Eight Walls W1-W8 Keep Parties Apart
- Brand-Wall, User-Wall And Anonymous 401 Table Tests
- Shared Tables Need Field-Level Tests, Then Auto Schema Gate
- Why it matters: A Test That Can Fail Is The Only Proof

**Quiz**
1. Which wall keeps one business's data away from another business? A) W1 Brand Wall · B) W6 Public Wall · C) W7 Data-Out Wall · D) W8 Sensitivity Hold · **Answer A**: W1, the brand wall, sits between businesses.
2. What should an anonymous read of a control table return? A) 200 with rows · B) A list of tenants · C) 401 · D) The sales page · **Answer C**: 401 means the signed-out request was refused, which is the pass.
3. Why is a row-level test not enough on a shared table? A) Shared tables have no rows · B) It is too slow · C) Shared tables are always public · D) A shared row has no tenant id, so the test can pass while fields leak · **Answer D**: On a shared table the leak test must be field-level, because a row-level test passes while leaking.
4. Who moves the app through the Schema gate? A) A person always clicks yes · B) The engine, automatically, when every line is done · C) The customer · D) The reseller club · **Answer B**: Schema is an auto gate: tables probed and names re-read, then the engine moves the app on.
